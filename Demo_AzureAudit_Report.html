About the vulnerability sources

CVE – Common Vulnerabilities and Exposures

A CVE ID (for example CVE-2024-12345) is the global name for one publicly known vulnerability. IDs are assigned by CVE Numbering Authorities such as Microsoft, Red Hat or GitHub, and the list is run by MITRE for the US government. cve.org holds the official record: a short description and references.

NVD – National Vulnerability Database

NIST's NVD adds analysis to each CVE: the CVSS score, the affected products (CPE) and the weakness type (CWE). CVSS v3 rates severity from 0 to 10: 9.0–10 Critical, 7.0–8.9 High, 4.0–6.9 Medium, 0.1–3.9 Low. CVSS describes how bad a vulnerability can be, not how likely it is to be used against you.

CISA KEV – Known Exploited Vulnerabilities

The US Cybersecurity and Infrastructure Security Agency keeps the KEV catalogue: vulnerabilities with reliable evidence of exploitation in real attacks, each with a required action and a due date for US federal agencies. A CVE on this list is the strongest signal for priority; this report marks it Known exploited and puts it in phase 1 of the action plan. "Ransomware" means the CVE is known to be used in ransomware campaigns.

EPSS – Exploit Prediction Scoring System

EPSS from FIRST estimates the probability that a CVE will be exploited in the next 30 days. It complements CVSS and KEV when many vulnerabilities have the same severity.

Microsoft Security Response Center (MSRC)

For Microsoft products, the Security Update Guide lists the security update (KB) that fixes each CVE, the affected versions and Microsoft's own exploitability assessment. The MSRC link only has content for Microsoft CVEs.

GitHub Advisory Database (GHSA)

GHSA IDs describe vulnerabilities in open-source packages (npm, NuGet, PyPI, Maven …). Most are also linked to a CVE.

Where the vulnerabilities in this report come from

Vulnerabilities in installed software are reported by Microsoft Defender for Cloud: Defender for Servers (Microsoft Defender Vulnerability Management) for VMs and Arc servers, Defender for Containers for images in Azure Container Registry, and SQL vulnerability assessment. The other tools in this report check configuration, not installed software, so they rarely mention CVEs. Any CVE or GHSA ID they do mention is picked up and shown here as well. If Defender's vulnerability assessment is not enabled, an empty list does not mean the environment has no vulnerabilities.

How to read this report

Findings and issues

A finding is one failed check on one resource. An issue groups every finding from the same check, so a missing tag on 300 resources is one issue with 300 findings. Prioritise by issue; use findings to plan the work.

Severity

Critical – directly exploitable or imminent outage risk, act now. High – significant risk, fix within weeks. Medium – best-practice gap to plan into regular work. Low – hygiene and optimisation. Info – informational or needs manual investigation.

Severities are normalised from each tool: Prowler, Maester and the built-in checks keep their own levels; Azure Advisor and WARA impact High/Medium/Low map directly; PSRule Critical/Important/Awareness map to High/Medium/Low.

Areas

Findings are grouped into Security, Identity, Governance, Reliability, Cost, Operations, Performance, Infrastructure and Compliance. Advisor and PSRule findings follow their Well-Architected pillar.

Overlap between tools

Several tools can report the same underlying problem (for example blob soft delete from both the built-in checks and Azure Advisor). Findings are kept per tool so nothing is lost; the Resources tab shows which sources flagged each resource.

Limitations

All tools run read-only with the permissions of the signed-in account. Checks that could not run because of missing permissions do not show up as findings, so a low count is not proof of compliance. Evaluate each recommendation against the organisation's requirements before changing anything.
